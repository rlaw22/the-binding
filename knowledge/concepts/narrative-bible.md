# Narrative Bible — The Binding

**Purpose**: Single source of truth for all narrative design rules across every adventure.

**Supersedes**: `narrative-design-spec.md`, `scene-design-framework.md`, `scene-manifest-template.md`, `scene-system-design.md` (narrative sections). Those files remain for historical reference but this document is authoritative.

**Last updated**: 2026-08-19

---

## Core Principles

1. **Immersion above all.** Never break the fourth wall. No meta-commentary, no DM scaffolding in displayed text.
2. **Player agency matters.** The player must feel they are making meaningful choices, not being funneled toward a single exit.
3. **Show, don't tell.** The narrative describes what the player sees, hears, and feels. It does not explain game mechanics.
4. **Scarcity creates tension.** Not every search yields treasure. Nothing-found items make genuine discoveries feel earned.

## Scene Manifest Structure

Every scene is a manifest object. Here is the **canonical field reference**, derived from actual code:

```javascript
{
  sceneId: 'scene_XX',
  sceneName: 'Human-Readable Scene Name',

  // Opening narration — the field is "description", NOT "narrative"
  description: 'Opening scene description. 2-4 paragraphs, vivid and atmospheric.',

  // Exit mechanics
  exitAction: 'exit_id',           // content item ID that triggers exit
  exitLabel: 'Action text for the exit button',
  hardExitNarration: 'What happens if the player refuses to leave after 75% completion.',

  // Location constraints
  // Keys are "banned" and "valid" — NOT "current"
  locationKeywords: {
    valid: ['inn', 'bistritz', 'golden krone'],   // locations reachable now
    banned: ['castle', 'borgo pass', 'london']     // locations NOT yet reachable
  },

  // Content items — the exploration buttons
  content: [
    {
      id: 'examine_X',
      label: 'Examine the X',
      discovery: 'What the DM reveals when the player does this.',
      outcome: 'positive',           // positive | negative | empty | mixed (see below)
      coinReward: 7,                 // NOTE: unused in Story Mode (see Coin Behavior)
      itemGained: 'item_id',         // only when this action newly awards an item
      keywords: ['examine', 'X']     // for action matching
    },
    // ... more items
  ],

  // Story Mode configuration
  storyMode: {
    // Bad choice (trap button) — every scene needs one
    badChoice: {
      id: 'bad_action',
      label: 'Do the dangerous but plausible thing',
      consequence: 'The consequence narrative. Pre-authored text describing what goes wrong.',
      coinCost: 3,                   // coins lost (default: 3 across all adventures)
      flagSet: { made_bad_choice: true }  // optional: flags that affect later scenes
    },

    // Optional: threat encounter (combat scenes)
    // In manifests, this is a STRING reference to a threat definition, not an inline object
    // threat: 'dr_wolves',

    // Optional: collectible item
    collectibleItem: {
      id: 'silver_dagger',
      label: 'Take the silver dagger from the wall'
    },

    // Dead fields — present in manifests but NOT read by any engine code.
    // Kept for potential future use. Do not rely on these for game logic.
    // isHealing: false,                 // generated by inject-storymode.js, never consumed
    // explorePriority: ['examine_X'],   // first 3 content IDs, generated but never consumed
  },

  // Initial facts for inventory/NPC sync
  initialFacts: {
    items: [],           // items the player starts this scene with
    metNPCs: [],         // NPCs the player has met (must match keyNPCs names/ids)
    established: []      // key plot points established in this scene
  }
}
```

### Inventory and Acquisition Integrity

Storyline inventory changes must be synchronized with authored narrative. A discovery or collectible button that newly gives, finds, takes, receives, or otherwise places an item in the player's possession **must** declare the appropriate acquisition contract (`itemGained` for content discoveries or `storyMode.collectibleItem` for collectible buttons). The deterministic Storyline engine owns the inventory mutation and appends explicit acquisition confirmation to the player-facing narration for both paths. Manifest authors must not hand-author or omit this confirmation.

Do **not** add `itemGained` when the player is merely examining, using, referencing, or carrying an item already present in `initialFacts.items` or carried forward from an earlier scene. In those cases, the discovery may describe the item but must not award it again.

Every acquired item must satisfy one of these contracts:

- **New acquisition:** content item has `itemGained: 'canonical_item_id'`; discovery clearly narrates the transfer or acquisition.
- **Already possessed:** the item appears in `initialFacts.items` or is carried forward; discovery only references or uses it.
- **No acquisition:** no inventory-changing language and no `itemGained` field.

Never rely on discovery prose alone to mutate inventory. Conversely, never award an item without visible narrative confirmation. Run the cross-adventure acquisition audit before merging manifest changes.

### Filler Action Integrity

Filler actions are generated centrally by the DM service, not authored per adventure manifest. They are atmospheric-only and must never invoke the LLM or create new NPC interactions, locations, discoveries, flags, or inventory items. A filler response must not advance scene completion or be treated as an exploration content item.

### ⚠️ Field Name Gotchas

| ❌ Wrong (in old docs/template) | ✅ Correct (what code actually reads) |
|---|---|
| `narrative` | `description` |
| `locationKeywords.current` | `locationKeywords.valid` |
| `initialFacts.npcGifts` | *(not used — NPCs give items via `metNPCs` + engine logic)* |
| `initialFacts.flags` | *(scene flags are set via `badChoice.flagSet`, not `initialFacts`)* |
| `presentCharacters` | **Dead field** — not read by any code. Do not use. |
| `storyMode.isHealing` | **Dead field** — set by inject-storymode.js but never read by engine. Safe to keep in manifests for future use. |
| `storyMode.explorePriority` | **Dead field** — generated (first 3 content IDs) but never read by engine. Safe to keep in manifests for future use. |

## Collectible Object Alignment

Every Storyline `storyMode.collectibleItem` must remain aligned across five layers:

1. The object physically described in the scene or discovery narration.
2. The exploration/pickup action and its target.
3. The collectible `id` and display `label` in the manifest.
4. The inventory display name shown after collection.
5. The generator/source data used to create or regenerate manifests.

A simple exact-text search is insufficient: narration may describe an object as “a sharpened ash stake” while the inventory label is “Wooden Stake.” Audits must therefore combine exact checks with semantic review. Keep Storyline collectibles separate from similarly named Campaign/D&D inventory catalog items unless the systems explicitly share an item contract.

The 2026-08-18 audit identified 75 collectible definitions across Dracula, Frankenstein, and Holmes and documented the required five-layer alignment. It did not establish systemic runtime enforcement: current code still contains inconsistent crucifix IDs/material labels (`crucifix`, `silver_crucifix`, and `brass_crucifix`), and `addItem()` only accepts IDs registered in the Campaign inventory catalog. Treat the earlier claim that the brass crucifix mismatch was fully corrected as stale. A shared Storyline collectible contract, normalization adapter, and regression audit are still required. Keep Storyline collectibles separate from similarly named Campaign/D&D inventory items unless the systems explicitly share an item contract.

## Content Density Rules

### Target: 6-8 content items per scene

| Category | Count | Purpose |
|---|---|---|
| Discovery / Lore | 3-4 | Reveals useful info, items, NPC dialogue |
| Atmospheric / Empty | 1-2 | Player searches but finds nothing; grounds the scene in reality |
| Negative / Mixed | 1-2 | Reveals bad news, unsettling info, or mixed outcomes |
| Bad Choice (trap) | 1 | Plausible trap button; every scene needs one |

### Why 6-8?

With only 4 items (the old minimum), the button area empties after 3-4 clicks. The player stares at 2-3 buttons where one is "leave." This creates the **funnel effect** — the player feels herded toward the exit.

With 6-8 items, even after 4-5 clicks, there are still 2-3 undiscovered items plus the exit. The scene feels explorable, not emptied.

### How the Player Sees Them

The manifest holds 6-8 items, but the player sees **up to 3 explore buttons at a time** (from `story-engine.js`: `content.slice(0, 3)`). As items are discovered, they become dimmed buttons and new undiscovered items surface. The full button area includes:

- Up to 3 undiscovered explore buttons
- Contextual AI suggestions (filtered, non-duplicate)
- 1 exit button
- 1 bad choice button (always last)
- **Max 8 buttons total** (frontend cap)

Discovered items stay visible as dimmed, non-clickable buttons after undiscovered ones — this is the anti-funnel mechanism.

## Outcome Types

Every content item SHOULD have an `outcome` field for documentation clarity. However, the story engine processes all non-threat, non-bad-choice content items through the same exploration path — the `outcome` field is **metadata for authors**, not runtime logic.

| Type | Description | Coin Behavior |
|---|---|---|
| `positive` | Standard discovery — useful info, item, or NPC dialogue | Author-intended reward (see Coin Behavior below) |
| `negative` | Bad news, minor setback, or unsettling info | Author-intended cost or zero |
| `empty` | Nothing found. Atmospheric prose only. | **Always 0 coins** — no reward, no cost |
| `mixed` | Good and bad together | Author-intended |

### Rules

- `empty` items MUST always award 0 coins. They exist for realism, not reward.
- `positive` items are the default. If no `outcome` is specified, treat as `positive`.
- The `outcome` field is **not consumed by the story engine at runtime** — it's a design annotation. The engine handles exploration uniformly.

### Coverage

| Adventure | Coverage | Notes |
|---|---|---|
| Dracula (Act 1, inline) | 100% | All 4 outcome types used. Gold standard. |
| Dracula (Acts 2-5, external) | ~85% | Missing `negative` and `mixed` types; some items lack `outcome` entirely |
| Frankenstein | 0% | No `outcome` field on any item |
| Holmes | 0% | No `outcome` field on any item |

New adventures should target 100% `outcome` coverage for authoring clarity, even though the engine doesn't consume it.

## Coin Behavior

### Story Mode Exploration

In Story Mode, **exploration actions award 0 coins**. The story engine's `processExplore()` always returns `coinChange: 0`. This means:

- The `coinReward` field on content items is **informational only** in Story Mode — it documents authorial intent but has no runtime effect.
- Coins are earned through **threat encounters** (fight/defend/run outcomes) and **free-text actions** (scored by the AI DM).
- **Keep setting `coinReward`** — it's valuable for planning coin budgets per scene and per adventure, even though the engine doesn't consume it directly.

### Bad Choice Coins

Bad choices always deduct coins. The `coinCost` field is enforced by `processBadChoice()`.

| Severity | Scene Range | `coinCost` | HP Loss |
|---|---|---|---|
| **Mild** | 1-5 | 3 (standard) | None — players start with low HP |
| **Moderate** | 6-15 | 3-5 | 5-15 HP (guideline, not hard rule) |
| **Severe** | 16+ | 5-10 | 15-30 HP (guideline, not hard rule) |

**Design note**: HP loss values are guidelines. Players start with low HP, so consequences should feel threatening but not instantly lethal. Favor coin loss and narrative setbacks over raw HP damage.

## Nothing-Found (Empty) Items

These are the `empty` outcome items. They serve a critical design purpose:

### Why They Exist

1. **Realism**: Not every corner of an inn hides a secret. If every search yields treasure, the world feels like a theme park.
2. **Tension**: When the player finds nothing, they wonder if they missed something. This creates doubt and engagement.
3. **Button stability**: They keep the button count higher without adding more lore to author.

### Design Rules

- **Must reference objects already in the scene narrative.** If the scene mentions a fireplace, the empty item can be "Search the fireplace mantel." It CANNOT reference something not in the description.
- **Mix of inviting and honest labels:**
  - Inviting: "Search behind the bar" (player expects to find something)
  - Honest: "Survey the empty rafters" (player knows it's a long shot)
  - Both are valid. Use a mix across scenes.
- **Atmospheric prose required.** "You find nothing" is not acceptable. The response should reinforce the scene's mood:
  - ✅ "The mantel is bare — just ash and a candle stub burned down to nothing. The wax has dripped onto the stone like frozen tears."
  - ✅ "You scan the rafters. Dust, cobwebs, and the dark stain of decades of smoke. Nothing useful — but the shadows up there seem to shift when you're not looking directly at them."
  - ❌ "You search but find nothing of note."
- **Maximum 2 per scene.** More than 2 empty items makes the scene feel barren.
- `discovery` must be `null` (not a string). The engine interprets `null` as "nothing found."

## Bad Choices

Every scene MUST have at least 1 bad choice (trap button).

### Design Rules

- **Must be plausible.** The trap should look like a reasonable action. "Open the coffin" is a trap; "Jump into the volcano" is not — no player would click it.
- **Consequence text is pre-authored.** The LLM adds atmospheric flavor, but the core consequence is written by the author.
- **Flag carry-forward is optional.** Mild traps can be self-contained. Moderate and severe traps SHOULD set flags that affect later scenes.
- **Labels must be unique across the entire adventure.** No recycling labels between scenes.
- **Labels must share at least one meaningful noun with the scene description.** A trap about a coffin makes no sense in a train scene.

### Severity Guidelines

| Tier | Scene Range | Consequence | Examples |
|---|---|---|---|
| **Mild** | 1-5 | Coin loss (3), atmospheric setback, no HP loss | Drugged ale, lost time, offended NPC |
| **Moderate** | 6-15 | Coin loss (3-5) + minor HP loss or item loss | Bitten by creature, trap triggered |
| **Severe** | 16+ | Coin loss (5-10) + major HP loss or story branching | Captured, ally killed, cursed |

### Structure

```javascript
storyMode: {
  badChoice: {
    id: 'drink_ale',
    label: 'Drink the innkeeper\'s offered ale',
    consequence: 'The ale is bitter and thick. Your vision swims. When you open your eyes, the fire has burned low and an hour has passed.',
    coinCost: 3,
    flagSet: { drugged_at_inn: true }
  }
}
```

## Button Ordering

The button area shows up to **8 buttons** total. The ordering is determined by the engine:

### Default (BACKGROUND / GENTLE pressure: 0-50% completion)

```
[ Undiscovered content items (up to 3 explore) ]  ← in manifest order
[ Contextual AI suggestions ]                      ← filtered, non-duplicate
[ Exit button ]                                    ← always present
[ Bad choice button ]                              ← always LAST
```

### Elevated (STRONG pressure: 75%+ completion, before hard exit triggers)

```
[ Exit button ]                                    ← moved to FIRST slot
[ Undiscovered content items ]
[ Contextual AI suggestions ]
[ Bad choice button ]                              ← always LAST
```

### Forced (FORCED: after hard exit triggers)

```
[ Exit button ]                                    ← only button shown
[ Bad choice button ]                              ← always LAST (if any remain)
```

### Discovered Items

Discovered items stay in the list as **dimmed, non-clickable buttons** (`.story-btn-discovered` class, opacity 0.35, dashed border). They appear AFTER undiscovered items. This prevents the funnel effect.

### Visual Styling

| Button Type | CSS Class | Border Color | Style |
|---|---|---|---|
| Explore | `.story-btn-explore` | Green (#27ae60) | Normal |
| Threat | `.story-btn-threat` | Red (#c0392b) | Normal |
| Item | `.story-btn-item` | Gold (#E8A838) | Normal |
| Ability | `.story-btn-ability` | Purple (#6B5CE7) | Normal |
| Bad choice | `.story-btn-bad_choice` | Grey (#555) | Italic, muted |
| Discovered | `.story-btn-discovered` | — | Opacity 0.35, dashed border |

## Exit Pressure System

The exit pressure ramp is **completion-relative, not turn-based**. The engine tracks what percentage of content items the player has discovered.

### How It Works

The engine uses `getPressureLevel()` which maps completion to a pressure level:

| Level | Completion | Condition | Exit Behavior | DM Pacing Instructions |
|---|---|---|---|---|
| `BACKGROUND` | 0-25% | Default starting state | Available, not highlighted (priority 4) | Rich scene descriptions, no rush |
| `GENTLE` | 25-50% | `completion >= 0.25` | Environmental cues (priority 4) | "The coachman coughs outside." |
| `STRONG` | 50-75% | `completion >= 0.75` | Moves to first button slot (priority 1) | "The candles burn lower. The coachman calls." |
| `FORCED` | After hard exit | `hardExitTriggered === true` | Hard exit executes (priority 1) | "The innkeeper locks the door. Time to go." |

**⚠️ Important**: At exactly 75% completion, pressure is **STRONG**, not FORCED. FORCED only activates after the hard exit mechanism triggers (see below).

### Hard Exit Mechanism

Two conditions must BOTH be true for the hard exit to trigger:

1. **Completion ≥ 75%** — sets `turnsSinceThreshold` to the current turn number
2. **4 more turns pass** after that threshold (`HARD_EXIT_TURNS_AFTER_75 = 4`)
3. **AND** at least **3 total turns** have been played (`MIN_TURNS_BEFORE_EXIT = 3`)

So a player who hits 75% on turn 2 won't get hard-exited until turn 6 (needs 3 min turns + 4 more). A player who hits 75% on turn 5 gets hard-exited on turn 9.

Once triggered:
- `hardExitTriggered = true` → pressure becomes FORCED
- The DM narrates the forced exit naturally using `hardExitNarration` — no game-y language
- **The player NEVER sees**: progress bars, completion percentages, turn counters, or visible pressure mechanics. The world just feels like it's winding down naturally.

## AI Suggestion Integration

The LLM generates suggested actions after each response. These are merged with the scene engine's structured content items.

### Deduplication

AI suggestions that overlap heavily with content items are filtered out. The **actual threshold** (from code):

- A suggestion is filtered if **≥50%** of its significant words (3+ chars, excluding stop words) overlap with any content item's label.
- This is stricter than the 70% mentioned in older docs.

### Supplementation

When content items are running low (2-3 undiscovered), AI suggestions fill the gap. The engine tracks used suggestions per scene to avoid repeats.

### Suggestion Count

The system prompt (`prompts.js` SYSTEM_PROMPT) says **"Provide as many as the scene supports — more for rich scenes, fewer for simple ones."** There is no fixed count — it scales with scene richness. The engine merges AI suggestions with content items and caps at 8 total buttons.

> **Note**: The separate `buildSuggestionPrompt()` function requests "Generate 4 specific actions" — this contradicts the system prompt and should be cleaned up separately. The system prompt is authoritative.

### LLM Button Injection — DISABLED

As of 2026-08-18, the **SUGGESTED ACTIONS parser has been removed** from `dm-service.js`. The LLM can no longer inject its own buttons. If the LLM generates a `SUGGESTED ACTIONS:` block in its response, it is **stripped from the narrative** before display.

**Why**: The LLM was generating buttons that contradicted the scene manifest — inventing characters from other scenes, referencing locations not in the current setting, and creating content that didn't match the curated scene design.

**What this means for authors**: All buttons the player sees come exclusively from the scene manifest's `content` array. The LLM's only job is narration. This gives authors full control over what the player can do in each scene.

## Scene Boundary Enforcement

The LLM must stay within the boundaries of the current scene. To enforce this, `buildSceneContext()` in the scene engine injects the following into every LLM prompt:

### What Gets Injected

1. **Scene setting** — the `description` field from the manifest (truncated to 500 chars)
2. **NPC list** — `initialFacts.metNPCs` with explicit "Do NOT include NPCs from other scenes"
3. **Established facts** — `initialFacts.established` (key plot points for this scene)
4. **Banned locations** — `locationKeywords.banned` (places the LLM must not reference)

### Example Injected Context

```
SCENE STATE:
Scene: The Coach Ride
Setting: The coach rattles through darkness so complete that the windows might as well be painted black...
NPCs present in THIS scene: driver, priest, two women in shawls. Do NOT include NPCs from other scenes.
Items available: crucifix.
Established facts: left the inn; riding in a coach at night; other passengers present (a priest, two women).
Completion: 0 of 6 explored
```

### Rules for `initialFacts.metNPCs`

**This field must list ONLY NPCs physically present in the current scene.** It is NOT a cumulative list of everyone the player has met.

| ❌ Wrong | ✅ Right |
|---|---|
| `['innkeeper', 'driver']` (scene_01 coach ride — innkeeper is at the inn) | `['driver', 'priest', 'two women in shawls']` |
| `['victor', 'elizabeth', 'caroline', 'waldman', 'krempe']` (scene_02 — not everyone is in every scene) | `['victor', 'waldman']` (only who's in THIS scene) |

**The engine uses this list to tell the LLM who exists in the scene.** If the innkeeper is in `metNPCs` for the coach scene, the LLM will narrate the innkeeper sitting in the coach — which is wrong.

### Rules for `locationKeywords.banned`

This list should include:
- Locations the player hasn't reached yet (e.g., `'castle dracula'` in Act 1)
- Locations from previous scenes that are no longer relevant (e.g., `'the inn'` in the coach scene)
- **NPC names from previous scenes** that the LLM might incorrectly bring back (e.g., `'innkeeper'`, `'old woman'`)

### Frankenstein & Holmes — NPC Boundary Audit Needed

Both adventures currently **accumulate NPCs** across scenes instead of listing only who's present:

| Adventure | Issue | Example |
|---|---|---|
| Frankenstein | scene_02 lists 6 NPCs from scenes 00+01 | Should only list NPCs in scene_02 |
| Holmes | Mostly correct but should be audited | scene_03 correctly drops Mortimer |

**Action required**: Run a pass over all Frankenstein and Holmes scene manifests to fix `metNPCs` to only list NPCs physically present in each scene. The scene `description` field is the authoritative source — if an NPC isn't mentioned in the description, they shouldn't be in `metNPCs`.

## Writing Conventions

### Scene Narrative (`description`)

- 2-4 paragraphs of opening description
- Every element mentioned can become a button (the player will try to interact with it)
- Use sensory details: sight, sound, smell, touch, temperature
- End with an implicit question or tension point (what will the player do?)

### Discovery Text

- 1-3 paragraphs revealed when the player clicks a button
- Must feel like a reward for exploring
- Should deepen the scene's atmosphere or advance the plot
- Reference objects mentioned in the opening narrative
- Minimum 30 characters per discovery text

### Nothing-Found Text

- Must reference objects already in the scene narrative
- Should reinforce the scene's mood (not just "you find nothing")
- See Nothing-Found Items section above

### Exit Narration

- `exitLabel`: Clear, atmospheric action text (e.g., "Board the coach into the darkness")
- `hardExitNarration`: What happens if the player refuses to leave after 75% completion
- Should feel like a natural progression, not a punishment

## DM Prompt Rules (Enforced at Runtime)

These rules are embedded in the system prompt (`prompts.js`) and enforced every turn:

1. **Narrative first** — every response paints a vivid scene with sensory details
2. **Agency matters** — never override player decisions; adapt, don't railroad
3. **Conciseness** — 1-3 short paragraphs (100-200 words); one strong image beats three average ones
4. **NPC dialogue** — 1-3 sentences max, no speeches
5. **Single actions only** — each suggestion must be ONE discrete action, never combined
6. **No meta-commentary** — never break character, never praise the player's choices, never say "clever move" or "well played"
7. **No player narration** — never describe the player character doing, holding, or saying something the player hasn't chosen
8. **Inventory truth** — only reference items actually in the player's inventory
9. **No mechanics exposure** — don't show DCs, HP, or internal numbers unless the player asks
